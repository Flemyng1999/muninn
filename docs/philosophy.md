# 设计哲学

## 一、解决什么问题

**在 AI 时代，个人知识管理崩溃的三种方式**：

1. **AI 瞎改**：你让 AI 帮你整理笔记，它擅自重写了你的核心定义，三个月后你发现这份笔记和那份笔记说的不是一回事
2. **重复定义**：同一个概念在 5 个笔记里被重复"解释"一次，措辞都不一样，互相矛盾也不知道
3. **孤儿笔记**：随手记了个想法，6 个月后它孤零零躺在某个角落，搜不到、用不上、也不敢删

KMS 就是为解决这三个问题设计的最小制度。

## 二、三个核心原则

### 原则 1：SSOT（Single Source of Truth）

**核心概念只在一个地方有权威定义**（`_Concepts/概念-xxx.md` 主卡）。其他地方只允许 `[[link]]` 引用，**禁止重写**。

**AI 违反这条的典型症状**：你让它写笔记，它在正文里写"光合速率（photosynthesis rate）是指单位时间内植物..."。错。应该写"...依赖 [[概念-光合速率]]..."。

### 原则 2：Arbiter-Executor 角色边界

**你永远是 Arbiter（决策者）。AI 永远是 Executor（执行者）。**

AI 可以：起草 seedling / 修 typo / 挂链接 / 跑整理
AI 不能：改核心定义 / 改 `_Governance/` 规则 / flip `authoritative` / 擅自删卡

实现方式：**R08 §8.7 编辑深度矩阵** —— 按操作动词分 🟢 / 🟡 / 🔴 三档，🔴 操作强制走 Q3 三要素授权（Arbiter 审阅 + 入链评估 + 书面判断）。**R08 §8.8 内容卫生**进一步约束长期卡片正文，避免短期任务状态、临时路线名和 agent 过程语污染 evergreen 知识。

### 原则 3：三层分离

| 层 | 内容 | 谁能改 |
|---|---|---|
| 宪法层 | `_Governance/@宪法.md` / `rules.yaml` / `schemas/` | 只有 Arbiter |
| 工作流层 | `_Skills/` | Arbiter 主导，AI 起草 |
| 数据层 | `_Concepts/` / `03-Zettelkasten/` / `00-Journal/` ... | Arbiter 主导，AI 起草 seedling |

层越高，改得越少。宪法 6 个月改一次，数据每天在变。

## 三、为什么用 Obsidian + Git

- **Obsidian**：本地优先，文件就是 Markdown，没有 lock-in；`[[双链]]` 原生支持 SSOT 引用；插件生态能做仪表盘（Dataview / Templater）
- **Git**：版本历史 = 你的第二个 memory；commit message 强迫你每天回顾；diff 让"改了什么"可追溯

选这两个不是因为它们完美，是因为它们**极其不流行**得突破门槛——大部分人能用上 Obsidian 就已经筛掉 80% "工具玩家"，只剩真的需要长期沉淀的人。

## 四、为什么不是 Notion / Roam / Logseq

| 工具 | 问题 |
|---|---|
| Notion | 闭源 + 云存储 + AI 权限模型差 + 不是纯文本 |
| Roam | 图式好但结构自由到没约束，AI 协作模型缺失 |
| Logseq | 接近 Obsidian，但插件生态不够，Outlining 范式强迫大纲化 |
| Google Docs | AI 原生差，SSOT 模型不存在 |

Obsidian + Markdown 是现阶段**最接近纯文本 + 最能建立规则边界**的组合。未来若有更好方案可迁移（纯 Markdown 没 lock-in）。

## 五、为什么要"宪法"这么重的词

因为没有它，AI 会乱来。

宪法不是为了控制你（你是 Arbiter，想改就改），是为了**让你有武器约束 AI**。当 AI 提议改你的核心定义时，你指着宪法 R08 §8.7 🔴 档，就能立刻拒绝它——不是因为你挑剔，是因为规则本来就不允许。

这套制度的真正价值不在"记笔记"，而在**让你和 AI 形成稳定协作关系**。没有规则，每次和 AI 协作都是从零谈判。

## 六、为什么分 profile

**共性**：SSOT / 角色边界 / 生命周期 / 时间戳 / 健康度 —— 这些对所有知识工作者都成立。

**差异**：沉淀对象不同。研究者沉淀论文 + 实验；产品人沉淀访谈 + 决策；工程师沉淀 ADR + 故障。

**设计选择**：把共性提取到 `core/`，把差异下沉到 `profiles/<domain>/`，用 overlay 合并。这样：
- core 改一次，所有 profile 受益
- profile 可以独立演化，不互相干扰
- 新 profile 的贡献门槛低（只写差异部分）

## 七、什么情况下别用

- 你的工作不需要跨月度沉淀（比如纯客服、纯执行） → 过度工程
- 你还没养成定期写日记/周报的习惯 → 先用 Notion 养 3 个月再考虑
- 你不打算和 AI 协作 → KMS 的一半价值消失
- 你只想做纯知识图谱玩具 → Logseq / Roam 更合适

诚实：这套系统**只对一部分人有用**。不要勉强。
