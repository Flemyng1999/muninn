# 2026-03-12 支付延迟突增事故复盘

## 一句话摘要

Pulsar 迁移 POC 期间双写流量超出 BookKeeper 集群容量规划，导致支付队列积压，最终用户支付中位延迟从 800ms 升至 12s，持续 47 分钟。

## 时间线（Timeline, UTC）

| 时间 | 事件 |
|---|---|
| 14:23 | POC 从 5% 流量调到 15%，正常 |
| 14:45 | BookKeeper ensemble 写入 p99 开始上升（被 2 min 后 Grafana 告警捕获） |
| 14:47 | PagerDuty 触发 SEV-3 告警（write latency p99 > 100ms） |
| 14:52 | On-call @carol 确认告警，开始排查。初步判断"可能是 POC 流量"，但不确定 |
| 14:58 | 用户支付开始受影响，中位延迟从 800ms 升至 3s。客服开始报投诉 |
| 15:02 | Incident Commander @bob 升级事故至 SEV-2 |
| 15:08 | 决定：回滚 POC 流量比例从 15% → 0%（即临时完全走 Kafka） |
| 15:10 | POC 流量 = 0%，Pulsar 写入停止 |
| 15:15 | 支付延迟仍然高（因为 Kafka 积压队列需要追赶） |
| 15:30 | 支付延迟回到 < 1s |
| 15:35 | 声明事故结束。用户可见影响 47 分钟（14:58 → 15:35） |

## 根因分析（Root Cause Analysis）

### 直接原因

BookKeeper ensemble 只按 10% POC 流量配置容量（3 节点 × 2TB SSD）。从 5% 调到 15% 时 2 个节点达 95% IO utilization，write latency 雪崩式上升。

### 次因

1. **容量规划基于预期而非 headroom**：10% 配置只对应 10% 流量，没有留 50% headroom
2. **监控盲区**：BookKeeper 单节点 IO util 不在日常 dashboard，需要 drill-down 才能看
3. **响应时间偏长**：从 p99 上升（14:45）到 IC 介入（15:02）用了 17 min，因为 on-call 不确定根因

### 没发生什么（避免 blame）

- 不是代码 bug
- 不是 Pulsar 4.x 产品 bug
- 不是人员操作失误（@carol 的 POC 流量调整动作按 SOP 批准）

## 可控因素（Action Items）

- [x] **立刻**：回滚 POC 流量 → 已完成 15:10
- [x] **当晚**：给 BookKeeper 加节点（3 → 5），磁盘 2TB → 4TB → 已完成 2026-03-12 23:00
- [x] **2 周内**：BookKeeper 单节点指标加入主 dashboard → @bob 完成 2026-03-22
- [x] **1 个月内**：所有新基础设施容量规划必须含 50% headroom 规则（已写入 [[概念-最终一致性边界]] 的"容量假设"节） → @alice 完成 2026-04-05
- [ ] **2 个月内**：事故响应 SOP 加一章"POC 期专项 oncall 升级规则"（p99 上升 + 在 POC 窗口 → 自动 SEV-2，不等人判断） → @carol owner，due 2026-05-01

## 经验教训（Lessons）

1. **POC 流量调整不是"测试"，是生产变更** —— 应走同样的变更管理流程
2. **容量规划写 50% headroom 不是保守，是工程纪律**
3. **让机器先判 SEV-2**：p99 上升 + 变更窗口 ≡ SEV-2，不要等人从 SEV-3 升级
