# 概念-最终一致性边界

## 定义

在 `payment-service` 系统里，**哪些操作可以接受最终一致性（eventual consistency），哪些必须强一致（strong consistency）**，由本主卡权威划定。

## 一致性分级表

| 操作 | 一致性要求 | 可接受延迟 | 技术实现 |
|---|---|---|---|
| 用户支付（写订单） | **最终一致** | ≤ 2s | Pulsar 异步复制 + 幂等 upsert |
| 支付回调（写状态） | **强一致** | 无延迟 | DB 行锁 + 事务 |
| 账户余额更新 | **强一致** | 无延迟 | DB 行锁 + 2PC |
| 对账流（T+1） | **最终一致** | ≤ 6h | 批处理 + 补偿机制 |
| 用户查询支付历史 | **最终一致** | ≤ 5s | 读副本（可能滞后） |
| 反欺诈规则查询 | **最终一致** | ≤ 30s | 异步规则引擎 |

## 边界条件（"最终"到底多久）

历史经验：
- 正常运行：最终一致的**最长实际延迟** < 500ms（p99）
- 高峰运行：< 1.5s
- 积压期：**最多 12 秒**（由 [[2026-03-12-支付延迟突增事故]] 定义的观测上限）

若 > 12s，则触发降级逻辑（同步兜底 + 告警）。

## 容量假设（2026-04-05 加入）

每次新增或修改本表中一致性要求时，必须附容量规划。规则：

1. **写 headroom ≥ 50%**：按峰值 1.5 倍规划容量
2. **读副本 lag < 500ms p99**：若超出则自动扩 follower
3. **队列 backlog 告警阈值 = 1000 条未消费**：早于延迟突增

这条纪律来自 [[2026-03-12-支付延迟突增事故]] 的 Action Item #4。

## 为什么"用户支付"是最终一致

**监管合规**：B 端支付服务，用户可接受 2s 写入确认延迟（行业标准）
**技术必要**：跨地域 + 多 instance 多写场景下强一致成本高 2 个数量级
**业务容忍**：用户发起 → 看到 "处理中" → 2s 后 "成功" 的体验已被验证可接受

若未来改变（如面向 2C 的即时支付），需要另起 [[ADR-0018-订单创建一致性重评估]]（未建）。

## 使用此主卡的规则

任何 ADR / PR / 会议里出现"最终一致性"或"强一致" → **一律 `[[link]]` 到本主卡**，不要在 Confluence / JIRA 票据里重新写一套分级。

历史事故：2024-08 有个 PR 因为没 link 本主卡，自行"合理化"把"账户余额"按最终一致写，造成 2 小时账户显示不一致 + 16 个客户投诉。从那以后强制走 SSOT。
